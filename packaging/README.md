# Zahlen toolchains

A Zahlen toolchain is the engine plus its optional packages, built once, and
consumed by developers without root. There are two channels, and they never
overlap:

| Channel | Owns | Installed by | Location |
|---|---|---|---|
| pacman (`packaging/arch/PKGBUILD`) | the manager binary | the distribution | `/usr/bin/zpkg` |
| `zpkg` | engine packages | the developer | `${XDG_DATA_HOME:-~/.local/share}/zahlen` (`%LOCALAPPDATA%\zahlen` on Windows) |

pacman ships exactly one file. Everything a project links against is the
developer's own copy, pinned per toolchain, installed and removed without
privileges. The manager itself is C++23 (`utils/zpkg`, a standalone CMake
project): it must run on a machine that has no Zahlen toolchain, so it cannot
link the engine, inherit its `-mavx2` flags, or be built inside its sanitizer
profile. It is built with `-fno-exceptions -fno-rtti` like the engine and
`zcook`, and reports failure with `std::expected` instead of throwing.

Enable packaging with `-DZHLN_INSTALL_TOOLCHAIN_PACKAGES=ON`. This profile
supports single-config Linux Release builds with the system libstdc++; the
engine is shared, the optional libraries remain static, and there is no
static-engine mode. The system simdjson must provide a CMake CONFIG package.
Packaging is opt-in outside Docker; the CI builder enables it.

## Packages

Each `Zahlen<Name>` install component has its own CMake config, version file,
exported targets, library and headers, plus two metadata files that let `zpkg`
work without a database:

* `share/zahlen/toolchain.json` — the toolchain id, version, commit, compiler,
  processor, profile and ABI hash.
* `share/zahlen/manifests/zahlen-<package>.json` — the package name, its
  component, the packages it requires and the targets it provides.

Both are read with simdjson by `zpkg` and refused outright if a key is missing or
has the wrong type, so a reordered or extended document can never be silently
misread.

Both are generated by `cmake/Toolchains.cmake`, which is the only place that
knows the dependency graph. Nothing hand-copies that graph any more.

CI produces one `usr/` archive per component from a **single** builder image and
uploads them as the `zahlen-toolchain-release` and `zahlen-toolchain-asan`
artifacts:

```
zahlen-<component>-<toolchain-id>.tar.gz
zahlen-<component>-<toolchain-id>.tar.gz  # one per component
SHA256SUMS
```

`<toolchain-id>` looks like `0.1.0-7c6e062-gcc-16.2.1-x86_64-release` and is
derived from the same inputs as the ABI hash, so an id can never describe two
different ABIs. Keep sanitized toolchains as separate ids; they install side by
side and are never overwritten.

| Component / config suffix | Installed target | Requires |
|---|---|---|
| Engine | Engine, Jolt | distro runtime libraries |
| CommandLine | CommandLine | system C++ runtime |
| Signal | Signal | Engine |
| HostRunner | HostRunner | Engine, CommandLine, Signal |
| Application | Application | Engine, CommandLine, HostRunner |
| UISchema | UISchema | Engine |
| Serialization | Serialization | Engine, UISchema, system simdjson |
| GLTF | GLTF | Engine, Serialization |
| Screenshot | Screenshot | Engine |
| Netpbm | Netpbm (header-only) | Engine |
| FreeCam | FreeCam | Engine |
| Camera | Camera | Engine, FreeCam |
| CharacterController | CharacterController | Engine, FreeCam |
| SkeletalAnimation | SkeletalAnimation | Engine |
| Animation | Animation | Engine, SkeletalAnimation, CharacterController, Camera, FreeCam |
| Cooker | zcook (installed as `bin/zcook`) | Engine |

All targets use the `Zahlen::` namespace. The `Requires` column is what the
archives themselves declare; `zpkg info` prints the same thing for what is
installed. CMake's native exports preserve static PRIVATE edges as `LINK_ONLY`;
in particular GLTF finds Serialization even though its public API does not
mention JSON. Named C++ module sources are installed; prebuilt BMIs are not
portable artifacts. The in-tree `zahlen_module` umbrella is not exported.

## Installing packages with zpkg

```sh
zpkg install ./toolchain-output              # every archive in the directory
zpkg install ./zahlen-engine-*.tar.gz        # or one at a time
```

`zpkg` verifies `SHA256SUMS`, refuses anything that would land outside `usr/`,
and refuses an archive whose `format` it does not understand. It does not
resolve dependencies: it installs what you name and then tells you, once, which
required packages are still missing. The install order therefore never matters —
every package of a toolchain installs into the same prefix.

```
$ zpkg install ./toolchain-output --require-checksums
  sha256 ok  0e2199a923a4d561...
  installed  zahlen-engine (Engine, 241 files) -> store/0.1.0-7c6e062-gcc-16.2.1-x86_64-release
  ...
active toolchain: 0.1.0-7c6e062-gcc-16.2.1-x86_64-release
prefix: /home/dev/.local/share/zahlen/store/0.1.0-7c6e062-gcc-16.2.1-x86_64-release/usr
```

| Command | Effect |
|---|---|
| `zpkg install <archive\|dir>` | verify, extract into `store/<id>/`, record the package |
| `zpkg list [--files]` | toolchains in the store, active one marked |
| `zpkg use <id>` | repoint `active` (future builds only) |
| `zpkg prefix [id]` | the prefix to hand to CMake |
| `zpkg env [id]` | shell exports for building and running |
| `zpkg info <id>` | compiler, profile, ABI, installed packages, requirements |
| `zpkg which <tool>` | resolve an engine tool, active or not |
| `zpkg shims enable\|disable` | `~/.local/bin` shims for engine tools |
| `zpkg remove <id>` | delete a toolchain, refused while it is active |
| `zpkg remove --package <name>` | delete one package from a toolchain |

`--only Engine,CommandLine,Data` installs a subset; `--require-checksums` makes
a missing or wrong checksum fatal, and `--require-signatures` makes an unsigned
release fatal.

## Trust and remotes

A release is signed once, by the publisher, with ed25519. The signature covers
the exact bytes of `SHA256SUMS` (for a directory) or `index.json` (for a remote),
one line per signer:

```
<fingerprint-hex> <base64 signature>
```

```sh
zpkg key add zahlen-release-key.pub --name "zahlen CI"   # trust, per store
zpkg install ./toolchain-output -s                        # refuse anything unsigned
zpkg index ./toolchain-output --out ./index.json          # describe a directory
zpkg remote add upstream https://packages.example.com/zahlen
zpkg install upstream:upstream -s                         # fetch, verify, install
```

The index carries the hash and size of every archive, so one signature over the
index covers a whole release, and downloads are content-addressed in
`cache/<sha256>`. A signature from an untrusted key is not an error: it is
reported and ignored, which is what lets a mirror sign a release it did not
build.

## Layout and the invariants behind it

```
$ZHLN_ROOT/store/<toolchain-id>/usr/{bin,lib,include,share}   # immutable payload
$ZHLN_ROOT/store/<toolchain-id>/zpkg/                         # what zpkg installed
$ZHLN_ROOT/active -> store/<toolchain-id>                     # relative symlink
```

* **No root, ever.** `zpkg` refuses to run as root unless `ZHLN_ROOT` is set
  explicitly, and refuses `/usr`, `/opt`, `/etc` and friends as a store root
  even then. Nothing in the engine runtime or the development flow needs
  privileges; the CI job proves it by re-executing itself as an unprivileged
  user before it installs anything.
* **Toolchains never share a directory.** `zpkg use` only moves the `active`
  link, so it cannot change the runtime of a binary that already exists: that
  binary recorded the store path of the shared object it linked.
* **No `LD_LIBRARY_PATH`.** Every installed library carries an `$ORIGIN` rpath
  and every toolchain keeps its libraries next to the modules that need them.
  Needing `LD_LIBRARY_PATH` to run a binary from the store is a packaging bug,
  and CI fails on it. (The deployment container is a different delivery: it
  copies a flat `dist/` into `/app` and still sets `LD_LIBRARY_PATH=/app`.)
  Development never depends on that.
* **The store is relocatable.** `active` is a relative symlink and no file in
  the store records an absolute path, so the whole directory can be moved,
  copied between machines or baked into an image.
* **Removal is exact.** `zpkg` writes each package's file list at install time,
  so `remove --package` deletes that package and nothing else.

## Consumer

```cmake
cmake_minimum_required(VERSION 3.28)
project(my_game LANGUAGES CXX)
find_package(ZahlenApplication CONFIG REQUIRED)
find_package(ZahlenGLTF CONFIG REQUIRED)
find_package(ZahlenScreenshot CONFIG REQUIRED)
add_executable(my_game main.cpp)
target_link_libraries(my_game PRIVATE
    Zahlen::Application Zahlen::GLTF Zahlen::Screenshot)
```

Configure with:

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_PREFIX_PATH="$(zpkg prefix)"
```

or `eval "$(zpkg env)"` once per shell. There is no `-DZHLN_INSTALL_...` flag to
remember and no prefix to keep in sync by hand: the toolchain store is the only
input, and `zpkg prefix` is the only thing that knows where it is.

Application **does not auto-install optional modules found in the engine build**.
Link and compose what the application uses:

```cpp
#include <Zahlen/App.hpp>
#include <CharacterController/CharacterController.hpp>
// Also find_package(ZahlenCharacterController) and link its target.
// application.Install([](ZHLN::Engine& e) { ZHLN::Character::Install(e); });
```

`WithDefaultModules` remains source-compatible but the base default pass is
empty. Existing games which relied on implicit fonts, terrain, interaction,
cameras, animation or authoring tools must explicitly install those systems.

## ABI and profiles

Each config checks the compiler family, architecture, dual ABI,
debug-container mode, Release configuration and an explicit sanitizer profile,
and compiles `cmake/probes/pr125280-static-member.cpp` in the consumer's own
toolchain. It does **not** pin a compiler version, a patch release or a
`__GLIBCXX__` header date. A version floor was tried and removed: GCC PR
c++/125280 rejects the static-member construct Jolt and these headers rely on,
and its fix was cherry-picked onto `releases/gcc-16`, which reports 16.1.1 on
both sides of the commit — so `VERSION_LESS 16.1.1` admits the broken compiler
and tells the user nothing. Compiling the construct separates them; GCC point
releases otherwise keep the libstdc++ ABI, and an older runtime is rejected by
the linker/loader with the precise missing `GLIBCXX_x.y.z` symbol. A shared fingerprint includes the engine revision,
compiler flags, Jolt public ABI definitions/options and the annotation setting;
mixing fingerprints is rejected even when package versions match, and so is
mixing packages from two toolchain ids.

Jolt is bundled in Engine with its own public usage requirements, not resolved
against an arbitrary system Jolt. A toolchain is tied to the engine revision and
compiler family that built it; it is not a compiler distribution or a promise of
ABI stability across revisions.

Sanitized consumers pass `-DZahlen_SANITIZER_PROFILE=asan-ubsan`; ASan/UBSan
compile and link requirements propagate and there is no automatic switch from a
release toolchain to an instrumented one. The asan-ubsan toolchain also installs
a compiled hook object (`lib/zahlen/zahlen_sanitizer_options.o`) that
`ZahlenEngineConfig.cmake` attaches to consumer executables. Its rules are
compiled in, so no suppressions file has to be found at run time, and the
configure step fails loudly if the object is missing rather than silently
running without hooks.

## Runtime data

The toolchain ships no content, only the tool that makes it. `ZahlenCooker`
installs `bin/zcook` and `share/zahlen/tools/export_metadata.py`; a project cooks
its own pack:

```sh
cooker=$(zpkg which zcook)
tools="$(zpkg prefix)/share/zahlen/tools"
"$cooker" ninja --out assets.ninja --source "$PWD" --engine-tools "$tools" \
    --self "$cooker" --no-blender
ninja -f assets.ninja          # writes ./data/base.pak
```

The engine then finds `data/base.pak` in the working directory, beside the
executable, or under `data/` of the build tree; `ZHLN_DATA_DIR` overrides the
search with the directory **containing** `data/`.

There is deliberately no Data package. What would have been in one is either a
build input or the sandbox's own scene: shaders are `#embed`ded into the
renderer, the default font is `#embed`ded in `src/gui/FontLoader.cpp`, and
`Kernel.cpp` only warns when no pack is present. Shipping it also made every
toolchain package depend on the asset pipeline, because the install rule copied a
`cook_assets` artifact -- which is why `--component ZahlenData` could fail with a
`COPY_FILE` error on a tree where the cooker had not run.

## What CI proves

`scripts/test-toolchain-install.sh` runs against the exact resolved builder, and
re-executes itself as an unprivileged user before doing any of it:

1. Component-install and archive each package once, then write `SHA256SUMS`.
2. Sign `SHA256SUMS` and `index.json` with a throwaway ed25519 key, trust it, and
   install a subset into the default per-user store with `--require-checksums
   --require-signatures` — no `ZHLN_ROOT`, no sudo — requiring every excluded
   component to stay invisible.
3. Require the installed cooker to resolve through `zpkg which`, to run from the
   store, and then to cook a pack in an asset root the consumer owns.
4. Move the store and require `zpkg prefix` and the cooker to keep working --
   zcook's rpath is relative, so a relocated store still runs it.
5. Require a tampered checksum, a `SHA256SUMS` the signature no longer covers,
   and an archive outside `usr/` to be rejected.
6. Stage only the self-contained project under `tests/installed/`, which owns its
   source files and prefab scene; no engine application source is copied.
7. Build the standalone consumer against the store only, with no `LD_LIBRARY_PATH`
   and no reference to the engine checkout in the generated build files. Its
   `main.cpp` calls the public `PrefabFactory::CreateBox` API.
8. Put the pack the consumer cooked where the engine looks for it, require the
   render log to report that it was mounted, force Lavapipe, run eight warm-up
   ticks, then one measured tick and capture.
   Fail on tick errors or Vulkan validation errors, including at teardown; a
   180-second timeout bounds hangs.
9. Check extent/buffer consistency, finite positive mean luminance, lit pixels and
   nonconstant image content. Encode the artifact through the installed
   `Zahlen::Netpbm` plugin using `ZHLN::Netpbm::EncodePPM`, preserving a valid
   readback even if content checks fail, and upload `cube.ppm`,
   `consumer-render.log`, `zpkg-list.txt` and the archives.
10. Require a wrong-profile configuration to fail.

The consumer is independent of `app/cube.cpp`, which remains the original
four-line example. This tests installed Application/Engine/Netpbm integration and
nonblank output, not execution of the engine repository's example, exact
geometry/color, golden pixels or performance. GLTF and Screenshot are packaged
and published but are not exercised by this prefab test.

`packaging/arch/PKGBUILD` builds `zahlen-zpkg`, which installs `/usr/bin/zpkg`
and nothing else. It compiles `utils/zpkg` with the distribution's compiler and
runs its test suite in `check()`. Run `updpkgsums` before publishing; the recipe
is not an authenticated binary repository.
